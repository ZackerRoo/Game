## Context

我们要从零开始构建“城市建造 × 灾害生存”游戏的 MVP。目标是验证核心循环：管理资源、建设城市并在灾害中生存。我们需要一个灵活的架构，以便从 MVP 扩展到更复杂的模拟系统。

## Goals / Non-Goals

**Goals (目标):**
- **可玩的 MVP**: 在一张地图上生存 30 天。
- **可扩展架构**: 后续能轻松添加新建筑、资源和灾害类型。
- **响应式 UI**: 清晰的资源反馈和警报展示。
- **性能**: 在至少 50x50 的网格地图上保持 60fps 流畅度。

**Non-Goals (非目标):**
- **多人游戏**: 仅限单人。
- **复杂音效**: MVP 阶段暂无声音引擎。
- **存档/读档**: 仅支持基本的会话持久化（若时间允许），非优先项。
- **移动端支持**: 优先专注于桌面 Web 端。
- **3D 画面**: 使用 Canvas 实现 2D/2.5D 等轴视角。

## Decisions

### 1. 技术栈: React + Canvas
- **决策**: 使用 React 制作 UI（HUD、菜单、警报），使用 HTML5 Canvas 渲染主要游戏世界。
- **理由**: React 擅长 UI 状态管理；Canvas 能提供渲染大量网格实体所需的性能。
- **替代方案**: DOM Grid（大地图太慢），WebGL/Three.js（2D MVP 有点大材小用）。

### 2. 游戏架构: 中心化状态 + 循环
- **决策**: 使用由自定义 Game Loop 类管理的中心化 `GameState` 对象，与 React 状态解耦。React 组件订阅状态变更或通过轮询更新 UI。
- **理由**: 游戏循环需要稳定运行（如 60fps），可能与 React 的渲染周期冲突。逻辑解耦可确保模拟流畅。

### 3. 实体系统: 组合优于继承
- **决策**: 实体（建筑、灾害）将由数据（组件）定义，而不是深层类继承。
- **理由**: 允许一个建筑既是“生产者”（电厂）又是“消费者”（需要燃料），组合更加灵活。

### 4. 构建系统: Vite
- **决策**: 使用 Vite 进行快速开发和热重载 (HMR)。
- **理由**: 现代 Web 应用脚手架的行业标准。

## Risks / Trade-offs

- **风险**: React 重渲染性能。
  - **缓解**: Canvas 渲染循环独立于 React。React 仅在数值显著变化时更新 HUD（使用节流）。
- **风险**: 模拟系统的复杂性。
  - **缓解**: MVP 模拟将基于 Tick（例如 1 游戏小时 = 1 现实秒），而非连续物理模拟。
